# v0.1.0 Evidence-First Release Design

Date: 2026-10-08

## Decision

Publish the existing application as an evidence-backed `v0.1.0` case study.
This release improves version identity, dependency maintenance, CI hygiene, and
public engineering evidence without changing lead classification, reply
generation, export rules, or data-handling behaviour.

The repository remains positioned as a Python workflow-automation case study.
CommerceOps Desk remains the full-stack flagship. This release must not imply
that E-commerce Lead Automation has accounts, a database, a standalone API, or
production messaging integrations.

## Options considered

1. **Evidence-first release (selected).** Add a single application version,
   modernise CI and development dependency constraints, document verification,
   and publish a verified release. This produces useful trust evidence with a
   small behavioural risk surface.
2. **English product expansion before release.** Add locale switching, English
   screenshots, UI automation, a public demo, and a video before tagging. This
   would improve presentation but mixes product work with release hygiene and
   materially delays a truthful first release.
3. **Tag the current commit unchanged.** This is fast but leaves ambiguous
   runtime version text, older Actions runtimes, and no visible release-quality
   evidence.

## Scope

### Included

- Define `APP_VERSION = "0.1.0"` in `services/version.py` as the sole runtime
  release-version source.
- Produce a small, testable display label containing both semantic version and
  the process-captured build SHA.
- Display that identity in the existing Streamlit footer.
- Allow pytest 9 with `pytest>=9.0.3,<10` and update matching documentation.
- Add weekly Dependabot checks for pip and GitHub Actions.
- Add visible CI and Release badges plus a concise engineering-evidence section
  to the English README.
- Replace legacy product and export names in the synthetic golden workbook and
  add a regression assertion that keeps its instructions aligned with the UI.
- Replace the session-only SHA-1 upload fingerprint with SHA-256 and validate
  the operator-configured model base URL as credential-free HTTP(S), retaining
  local HTTP endpoint support for controlled deployments.
- Verify Python 3.10 and 3.12 in GitHub Actions, then create an annotated
  `v0.1.0` tag and a non-draft GitHub Release whose evidence links are fixed to
  the released tag and final CI run.
- Enable Dependabot security updates and keep CodeQL, secret scanning, push
  protection, and private vulnerability reporting enabled.

### Excluded

- Changes to classification rules, reply policy, workbook schemas, export
  eligibility, model calls, or session limits.
- Real customer data, claimed accuracy or conversion metrics, testimonials,
  stars, or usage counts.
- A public upload deployment. The current application has no authentication or
  durable audit controls, so a public data-ingestion endpoint is not release
  evidence worth the privacy risk.
- A `full-stack` repository topic or full-stack positioning.
- English localisation, UI browser automation, social preview artwork, and a
  demo video. These form a separate product-presentation iteration.

## Components and data flow

`services/version.py` owns the immutable release version and the existing build
SHA normalisation. A pure function combines the two into a display label.
`app.py` imports that label for the existing footer. No uploaded data enters the
version module, and no additional network request is introduced.

Repository maintenance files control CI and dependency discovery only. Runtime
requirements remain pinned as they are; pytest remains a development-only
dependency.

## Error handling and safety

- Missing or empty build metadata continues to render as `dev`.
- A long build value remains truncated to twelve characters.
- Upload fingerprints are used only for in-session deduplication, but use
  SHA-256 so security tooling does not need to distinguish that purpose from a
  cryptographic use.
- Model endpoints reject non-HTTP(S) schemes, embedded credentials, queries, and
  fragments. This does not turn an operator-selected third-party endpoint into
  a trusted service.
- Version display must not read Git state during a running process; the launcher
  continues to capture the SHA once at startup.
- Release publication stops if local tests, GitHub Verify, CodeQL, tag-to-commit
  checks, or remote SHA checks fail.
- Release notes explicitly describe production boundaries and use only
  synthetic-data evidence.

## Testing and acceptance

1. Add tests for the semantic version and combined release label first, and
   observe them fail before implementation.
2. Run the complete collected suite under pytest 9, including the new version,
   fixture, upload-signature, and endpoint-validation assertions, and review
   any warnings before release.
3. Compile `app.py`, `services`, and `tests`; run `pip check`.
4. Validate workflow and Dependabot YAML and scan tracked history for common
   secret patterns.
5. Require the GitHub Verify matrix on Python 3.10 and 3.12 and a successful
   CodeQL run for the final release commit.
6. Confirm local `main`, remote `main`, the annotated tag's peeled commit, and
   the GitHub Release target all resolve to the same SHA.

## Rollback

Before tagging, changes can be reverted through the release pull request. After
publication, the maintainer will treat the tag and release as immutable
evidence; corrections use a new patch version instead of rewriting the
published tag.
